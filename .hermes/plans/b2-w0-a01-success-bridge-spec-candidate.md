## Idempotency, crash and other outcomes

Normal success yields exactly one pass event/receipt/binding and one completed claim/backlog; finalizer yields one tuple and result binding. Proposed exact bridge retry must first authenticate and apply an explicitly decided historic-read policy, then compare every immutable key and digest and return the recorded receipt only if all match, with no second append or invocation. Same identity with different evidence conflicts. **BLOCKED:** current completion requires a running run and is not this retry API; historic read authorization, operation encoding, commit-uncertain reconciliation and recovery are not established. Do not assert an automatic retry or safe redispatch. After a host commit but before its reply, the pass event and host evidence may exist without final tuple; inspect durable evidence under applicable authority. A pre-commit validation or statement failure rolls back that transaction's mutations, though earlier stage effects remain. A failed commit with uncertain durability requires inspection rather than a rollback assumption. A lost reply after a durable commit leaves the committed evidence present; recovery remains unimplemented. Finalizer pre-commit interruption rolls back tuple and binding together; after a durable commit before reply both exist, while an uncertain commit also requires durable inspection. Its existing authorized stored-result branch can return stored evidence for a matching expectation, but service revocation, changed fence or bindings can prevent a first finalization or read. An accepted activation without a recoverable result can be refused redispatch ([review_host.rs](../../crates/foundry-line/src/review_host.rs:2719)); a crash after stage collection but before completion can strand a running run and claimed work. Recovery remains BLOCKED.

Success-only does not globally suppress terminal completion. Current Held completion records terminal run, result and hold with current order predecessor, keeping claim/backlog claimed. Current Failed completion records run/result and completes claim/backlog; neither appends this proposed S1 event ([review.rs](../../crates/foundry-ledger/src/product/review.rs:832)). The host engine-run error branch calls `fail_review_dispatch`, which under its active fence marks the running run failed, stores counters and a failure diagnostic, and commits; it does not insert a host result or complete the claim/backlog in that transaction ([review.rs](../../crates/foundry-ledger/src/product/review.rs:809), [review_host.rs](../../crates/foundry-line/src/review_host.rs:1340)). Other errors, including failure of that diagnostic path or errors outside that branch, can leave a run and claim stranded. Earlier stage and external effects may already exist. Failed status or error does not prove a domain rejection; Held, Failed, error, continuation and their S1/recovery policy are BLOCKED, and cannot satisfy the positive test. Preserve the existing B1 terminal paths and human hold decisions; do not use state-only classification or assume a retroactive bridge for legacy waiting orders. Legacy no-backfill policy remains BLOCKED. Existing B1 fixture counts and immutable accepted predecessor stay unchanged.
