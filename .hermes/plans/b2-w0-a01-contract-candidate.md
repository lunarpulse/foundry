Poll failure and drain/claim ordering must be considered when testing; do not infer no committed work from an error response.
- The existing feature-gated `prepare_p2_review_fixture` directly changes backlog to ready and can append `DieStarted`, `DieSucceeded`, and `InspectionPassed` (`crates/foundry-ledger/src/product/result.rs:415`, `:448`, `:461`). It is not the A01 path. `DieSucceeded` contains an attempt, not the produced commit.

- The real host accepts `ExecutionIntent` and `ProductWorkClaim`; it checks the claim, validates intent and pack, and admits activation (`crates/foundry-line/src/review_host.rs:863`, `:907`, `:926`, `:934`). Tuple and result binding commit together (`:1233`). - B1 requires current authority before a new external stage but allows collection and persistence of an already accepted stage after service revoke; it denies the next new stage (`docs/design/b1-scope-architecture.md:238`). An Owner's task execution authorization is distinct from service DriveReview and from human result approval.

## Proposed end-to-end flow and ownership

Names prefixed `proposed` below do not exist and are design placeholders. Each transaction is owned by the real ProductStore on one SQLite database; passing a path or making consecutive calls does not make them atomic. The coordinator lives in the product binary assembly, with a port pointing toward a producer; watch must not depend on line and ledger must not depend on exec implementation. Exact module/API placement remains BLOCKED.

1. **Entry and intake.** Invoke the actual `product_watch_cmd` via the product binary and its normal configuration. The proposed test would configure `product_github_tick` to use a local test provider endpoint, real poll/drain and real ProductStore to persist a source-bound delivery, admission S1 receipt and acknowledgement. Evidence: delivery ID, immutable source identity/revisions and raw snapshot/digest, admission order/lifecycle/sequence/hash, acknowledged inbox and `waiting_unsupported` backlog. The source, credentials, provider response, and initial source/service grants are synthetic fixture preconditions; no external GitHub claim. The CLI hardcodes `allow_loopback_http: false` (`crates/foundry/src/main.rs:2742`); test-only transport injection into the actual binary is unresolved and BLOCKED. Production transport safety must not be relaxed.
2. **Owner authorization and ready.** A proposed authenticated product endpoint/command calls `ProductStore::authorize_a01_task` with session, request key, admission coordinates, raw delivery ID, raw task kind and payload digest, fixed authorized kind/bytes/digest, and source. In one `BEGIN IMMEDIATE`, validate Owner identity, current scoped execution capability and source/admission, immutable raw input and request identity; insert a durable task authorization/receipt and transition the matching backlog `waiting_unsupported` to `ready`. A distinct capability and its grant/bootstrap surface are missing: Owner role alone is not scoped access under B1. DriveReview cannot issue this authorization. Evidence: actor, scoped authority/grant revision, separately bound raw delivery ID, raw kind and payload digest, authorized kind/bytes/digest, request digest/receipt and ready row committed together; original admission and snapshot unchanged. Until capability, endpoint and transactional representation are resolved this step is BLOCKED.
3. **Claim.** A later actual product watch invocation uses `claim_product_work_for_service`; proposed coordinator consumes its returned `ProductWorkClaim` and loads the matching authorized task via a proposed typed `AuthorizedTask` without substituting the raw payload. A proposed new-execution reservation must validate current service/source, exact task authorization and its scoped grant revision, claim owner/epoch/fence and lease inside its transaction; revision matching is proposed A01 policy, not an existing B1 task rule. Changed grant ABA must not silently authorize a new execution. Evidence: claim/backlog/service binding and counter, and a recorded task-to-admission/claim link. Claim's current digest remains the raw intake digest; current claim validation alone does not validate the new task.
4. **Producer and S1 — BLOCKED.** A proposed `ProductProducer::produce(AuthorizedTask, ProductWorkClaim) -> ProducerOutput` uses a test-only, side-effect-free fake. For each run derive distinct full-length syntactically valid fake base/result OIDs from a test nonce; they are strings, not Git objects. A candidate reservation records the operation and `DieStarted` under current authority and the exact worker fence; candidate completion persists accepted output and `DieSucceeded`, moving to Inspecting. Producer acceptance and recovery semantics are unresolved: do not assume the producer has B1 stage semantics, bypass the worker fence, or require a newly current grant in a way that discards accepted output. Persisting an accepted output and authorizing another execution are separate decisions.
5. **Review and finalization — BLOCKED.** The real `Inspecting` state serializes as `review` and is rejected by the current admission checks, which list the unrelated literal `inspecting`. Thus Inspecting → host is not currently available even before the missing bridge is considered. A passed host result does not itself establish the S1 transition to waiting in the shown path; a product-owned bridge, its authority, atomicity, receipt, timing and interaction with holds must be established before first finalization. The existing accepted-hold outcome requires waiting already, and a held host result is not eligible for first finalization; `ReviewHeld` could move Inspecting to waiting in the domain but a production bridge doing so here is not established. The older independent review design says active or waiting review remains Inspecting and only a bridge emits the completed inspection event (`docs/design/independent-review-engine-design.md:96`); its applicability or supersession by B1 product behavior is unresolved. P2's pre-host `InspectionPassed` reaches waiting but is fixture behavior, not proof that a producer may declare review passed. Thus neither pre-host InspectionPassed nor Inspecting → host → bridge → waiting is implementation-ready. Do not infer a change to B1 or use a direct host/finalizer wrapper until its preconditions and bridge are proven. Preserve separate host and finalizer transactions and accepted outputs after revoke. Once resolved, compare durable producer OIDs with intent external ref, host binding/result and tuple, as well as source, order, lifecycle, attempt, run, activation, worker/epoch/fence, raw identity and separate task authorization/digest; existing v3 result wire is not assumed to contain the new task digest.

**Assembly constraint:** the proposed integration test launches the actual binary/watch command against temporary SQLite and a local fixture provider, calls the proposed Owner surface, then invokes watch again with test-only producer injection reaching the same coordinator. A separate process cannot expose its in-memory call count: a candidate test-only structured stdout event or pipe must report entrypoint, invocation count, exact task/claim and raw fake output; correlate it with durable records. The local provider must record a request and return a per-run response canary, which is checked in the admitted raw snapshot, proving the binary used that provider. Test-built assembly, producer injection and safe loopback transport injection are BLOCKED pending design; no production default or safety relaxation. Provision source, service and Owner through real setup APIs, but do not seed ready, producer output, S1 transitions, host acceptance, tuple or result binding. No P2 helper. Synthetic provider and test executor do not prove a real provider, Die or isolation.

## Candidate errors, identity and transaction boundaries

These classifications are candidates, not existing API guarantees. Proposed new authorization validates envelope, session, current scoped Owner execution authority, raw delivery ID/kind/payload digest and admission, separately authorized kind/bytes/digest, and scoped authority/grant revision; it binds these and operation version, source identity/generation/revisions, order/lifecycle, admission seq/hash and expected backlog state in the `(actor_id, request_key)` request digest and immutable receipt. A changed field under the same key conflicts; a different actor is a different identity. No retry creates a second authorization or ready transition. The ordering of malformed input, denied authority, changed request and stale source/admission is unresolved: the earlier candidate ordering (invalid → current authority → key lookup → binding → state) could deny historic exact receipt reads after revoke. An alternative is authenticated and authorized historic receipt read before current execution-grant checks; its disclosure and read authority need decision. B1's existing result-finalizer service-first lookup is a separate rule and does not establish this new receipt policy. Preserve existing receipt bytes; exact retry returns stored bytes only if the eventual read policy authorizes it, and never grants new execution. Error precedence and compound cases remain BLOCKED.

For a proposed producer reservation, current service/source authority, exact claim/lease/fence and task authorization including grant revision must be validated for new execution; changed grant ABA cannot silently revive it. Whether revision matching or fresh human authority is required at each host stage is a proposed conditional A01 rule, not B1 behavior, and may conflict with B1 collection of accepted stages and results after service revoke. Do not impose it until its effect on B1 accepted evidence is resolved. Completion/persistence of an accepted output is distinct from reservation and must preserve accepted bytes without weakening the worker fence; producer-specific acceptance, expiry, regrant and safe recovery remain BLOCKED. Candidate operation identity covers authorization receipt, admission, attempt, worker/epoch/fence and input digest; same identity/different output conflicts. For the existing host/finalizer, current service check precedes stored-result lookup; first finalization can fail on stale binding or ineligible state, and failed accepted hold classification precedes live-currency checks (`product/result.rs:693`). Compound ordering beyond those paths remains BLOCKED.

## Scope exceptions and compatibility

M9's B2 allowlist includes product `main.rs`, line host/executor/lib, serve `lib.rs`, selected watch files, configuration-only blueprint/workflow/exec, related tests and docs (`.specs/m9-plan.md:367`); it excludes `foundry-ledger`, watch intake/worker and serve `auth_http.rs`/`review_hold.rs`. Candidate Owner authorization and atomic ready, producer/S1/receipt and output binding require a ProductStore transaction owner, so likely exceptions are `crates/foundry-ledger/src/product.rs` and/or `product/result.rs` plus any relevant ledger schema/migration and exports. A new HTTP route in `auth_http.rs`, an intake-worker change, or a task-bearing `foundry-exec` DTO/wire are separate exceptions where outside the permitted configuration/binding extension; identify exact files only after interface design. Product main orchestration and host wiring are in the list; tests are permitted, but cannot authorize the ledger changes themselves.

Least-invasive alternatives: (a) reuse current raw snapshot/digest and P2 helper: avoids a schema change but supplies neither explicit Owner task authority nor a separately bound fixed task and manufactures tested outputs; reject for A01. (b) keep authorization/output in process memory or a separate DB/file: avoids ledger schema but cannot atomically bind ready/S1/receipt to authority and crash recovery; reject for the proposed atomicity. (c) additive ProductStore rows in the same database and transactions, preserving existing ledger and receipt bytes: candidate, but no proof yet of exact schema, migrations, new capability, or result-wire representation. A separate additive result-to-task binding may avoid altering immutable v3 receipt bytes; verify that it provides the required result/approval binding and cannot be omitted by old writers. Changing existing wire or claim payload would require explicit versioning, readers, strict parsing and historical compatibility analysis, not assumed necessary or approved. Existing finalizer compares its work digest against the raw order payload (`product/result.rs:856`); replacing that digest with the task digest would break its present invariant.

Old binaries or already-open connections could bypass new guards or write an unbound state; version checks on new opens alone do not fence them. Before any future migration choose writer quiescence/fencing, backup and restore/reconciliation, compatibility for historical receipts, and crash behavior; no schema v4 or migration is claimed here. A reviewed scope exception is a decision about repository changes, not permission to write a production database or external repository. No such exception is approved by this draft.
