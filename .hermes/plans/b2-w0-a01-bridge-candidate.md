## Source facts and conflict

* `DieSucceeded` moves Working to Inspecting; the canonical serialized state is `review`, not `inspecting`. InspectionPassed and ReviewHeld move Inspecting to FurnaceHold (`waiting`); InspectionPassed also permits waiting → waiting. InspectionFailed can advance the attempt and requeue or fail, depending on its reason and attempt ([order.rs](../../crates/foundry-domain/src/order.rs:88), [transitions](../../crates/foundry-domain/src/order.rs:250)). Product review checks at [review.rs:423](../../crates/foundry-ledger/src/product/review.rs:423), [472](../../crates/foundry-ledger/src/product/review.rs:472), [2454](../../crates/foundry-ledger/src/product/review.rs:2454), and [2632](../../crates/foundry-ledger/src/product/review.rs:2632) list `inspecting`, not `review`. Each applicable admission/validation check needs examination; replacing only the first leaves other checks inconsistent. This is a source finding, not a tested run.
* Initial host completion writes run/result and optional hold, retains a claimed work item for Held, and marks claim and backlog completed for Passed/Failed in one transaction; it currently appends no S1 event ([review.rs:832](../../crates/foundry-ledger/src/product/review.rs:832)). The held row captures the current per-order predecessor. A resumed completion handles a new hold and retains the accepted predecessor ([review.rs:1460](../../crates/foundry-ledger/src/product/review.rs:1460)). Human terminal hold finalization separately appends a domain event and updates hold progress/result in one transaction; Resume is not a terminal S1 outcome ([review.rs:124](../../crates/foundry-ledger/src/product/review.rs:124), [2002](../../crates/foundry-ledger/src/product/review.rs:2002)).
* First result finalization requires `waiting` and runs in a separate transaction from the host ([result.rs:837](../../crates/foundry-ledger/src/product/result.rs:837), [review_host.rs:871](../../crates/foundry-line/src/review_host.rs:871)); tuple and binding commit together ([result.rs:1233](../../crates/foundry-ledger/src/product/result.rs:1233)). Held is not an eligible first finalized result. A host terminal result does not establish that every stage was accepted, nor that a final product result or human approval exists.
* The older [independent review proposal](../../docs/design/independent-review-engine-design.md:96) says active/waiting review remains Inspecting and only a bridge translates completed inspection. [T30](../../docs/design/t30-durable-execution.md:223) describes a `ReviewHeld` transition to FurnaceHold and a waiting pass self-loop, with its stated implementation limitations. Shipped B1 ProductStore hold acceptance/outcome and first result finalization require waiting ([product.rs:3062](../../crates/foundry-ledger/src/product.rs:3062), [review.rs:160](../../crates/foundry-ledger/src/product/review.rs:160), [result.rs:837](../../crates/foundry-ledger/src/product/result.rs:837)). These sources conflict in intended state semantics; none establishes that the older proposal was superseded.
* P2's feature-gated fixture preloads `DieStarted`, `DieSucceeded`, and `InspectionPassed` before host execution ([result.rs:415](../../crates/foundry-ledger/src/product/result.rs:415), [448](../../crates/foundry-ledger/src/product/result.rs:448)). It is legacy waiting setup, not proof of A01 producer/review wiring. Existing finalizer replay fixture asserts five ledger events, one tuple and one result binding, and preserves completed claim and receipt bytes ([b1_product_results.rs:1425](../../crates/foundry-line/tests/b1_product_results.rs:1425)); existing continuation fixtures include multiple generations and holds ([b1_product_results.rs:1800](../../crates/foundry-line/tests/b1_product_results.rs:1800), [4680](../../crates/foundry-line/tests/b1_product_results.rs:4680)). Preserve their exact counts, predecessor and evidence; do not backfill events.

The two prior review logs are untrusted inputs, reconciled against source above. Reviewer 0 proposes translating every Failed to InspectionFailed; reviewer 1 warns that infrastructure or budget outcomes must not become domain rejection. The latter caution is decisive: `ReviewDispatchCompletion` has status, counters, HostResult and optional hold but no typed domain failure reason ([review_run.rs:384](../../crates/foundry-exec/src/review_run.rs:384)). The host chooses Failed for a non-passing outcome without a hold, while execution errors take a separate `fail_review_dispatch` diagnostic path ([review_host.rs:1340](../../crates/foundry-line/src/review_host.rs:1340), [1453](../../crates/foundry-line/src/review_host.rs:1453), [review.rs:809](../../crates/foundry-ledger/src/product/review.rs:809)); budget exhaustion can also surface as an error ([review_host.rs:3509](../../crates/foundry-line/src/review_host.rs:3509)). Neither status nor exit code proves an inspection rejection. **Failed classification and its S1/claim disposition are BLOCKED**: do not invent a fixed reason, consume an attempt, or specify retry/replay semantics. Explicit human CommitFail/Abort already have their own established mappings; that does not classify host Failed.

## Alternatives — untested candidates

**A: conditional ProductStore bridge.** Conditionally prefer this for A01 if explicitly authorized: use the ProductStore transaction that records the applicable host completion to append the corresponding S1 event and transition receipt, with exact predecessor and fence. For a new A01 execution in `review`, initial Passed could append InspectionPassed; initial Held could append ReviewHeld before capturing the hold predecessor. This makes `waiting` include unresolved review holds and is a material interpretation of S1, not merely wiring. Preserve legacy waiting behavior and human hold actions. All failure and continuation details below remain decisions, not a contract.

**B: hold acceptance in `review`.** Keep S1 Inspecting during active/held work, as the older proposal describes, and change ProductStore hold acceptance, continuation/outcome and any dependent approval/finalization checks to support it; emit a domain event only at an agreed completed outcome. This changes B1's current waiting preconditions, predecessor and authorization-sensitive paths, and needs compatibility analysis and explicit change control. It is not demonstrated safer. Both alternatives require resolving the canonical state mismatch; neither is implementation-ready. A's `waiting` interpretation remains subject to the static consumer audit and its limitations below; external clients and dynamic behavior remain unverified.

Automatic actor, authority, operation/receipt identity, exact durable A01 provenance, crash recovery and out-of-allowlist change control are unresolved. No code, frozen contract, test result or scope approval is implied.

Do not suppress `complete_review_dispatch` globally or claim a failure is effect-free. Current terminal Held commits host evidence/hold and leaves claim/backlog claimed; Failed commits host evidence and completes claim/backlog; neither path appends an S1 bridge. Host execution errors use a separate diagnostic path. Held/Failed or host error cannot pass the positive A01 test and their actual durable effects must be reported. Existing B1 accepted-stage collection and legacy terminal persistence remain unchanged; broader hold/failure semantics and recovery remain BLOCKED and cannot be represented as solved by the test-only seam. ## Atomicity, authority and evidence

For A, a candidate initial completion transaction should validate exact order/lifecycle/attempt, source/admission, run/activation and original worker owner/epoch/fence, then atomically commit terminal run and host result, the applicable S1 event and trigger-created receipt, optional hold with its correct post-event predecessor, and existing claim/backlog disposition. The equivalent resumed transaction must account for accepted hold, progress, follow-up binding and repeated hold; it cannot be assumed equivalent to initial completion. Capture before/after snapshots and prove all-or-none at each proposed boundary. Existing S1 uses a per-order predecessor for intent/CAS, but the ledger event hash chains to the latest **global** ledger hash; interleaved orders must not be mistaken for predecessor changes ([review.rs:153](../../crates/foundry-ledger/src/product/review.rs:153), [189](../../crates/foundry-ledger/src/product/review.rs:189), [product.rs:841](../../crates/foundry-ledger/src/product.rs:841)).

The candidate needs an explicitly authorized service/system actor and operation identity for automatic bridge events, with receipt binding to the host outcome and exact A01 provenance. Do not impersonate the human hold decision actor or treat DriveReview as Owner task authorization or product approval. Decide the actor, authority, idempotency/read policy, and transition-intent representation before implementation. An acceptance receipt and its predecessor must remain immutable; no history rewriting. Preserve original accepted stage evidence and the original worker fence after service revoke; B1 permits collecting an already accepted stage result after revoke but requires current authority and fence before a new external stage ([b1-scope-architecture.md:228](../../docs/design/b1-scope-architecture.md:228)). This guarantee does not establish permission to start new work, nor does it establish blanket terminal/finalizer authorization after revoke. Extra A01 grant checks at collection are unresolved if they could discard accepted evidence. Current finalizer checks service before stored result and can reject first finalization on stale bindings ([result.rs:650](../../crates/foundry-ledger/src/product/result.rs:650)). Reconcile uncertain commits by inspecting durable evidence under applicable authority; no unauthorized retry protocol is proposed.

Host completion and the proposed bridge would be one ProductStore transaction only if actually implemented together; the result finalizer remains separate. Thus terminal evidence may exist without tuple/result binding, and failure of the latter does not roll back host or earlier stage effects. Current completion marks Passed/Failed work completed but holds remain claimed; a completed claim's owner/epoch/fence and backlog must not be rewritten by bridge/finalizer or silently reclaimed as a replay protocol. Existing fixture verifies completed claim is preserved even after lease expiry ([b1_product_results.rs:2022](../../crates/foundry-line/tests/b1_product_results.rs:2022)); public reclaim and ABA have separate checks ([b1_product_results.rs:4255](../../crates/foundry-line/tests/b1_product_results.rs:4255)).

Under A, waiting on an unresolved hold must not itself authorize final product approval. Approval requires current human authority and a strict local result/tuple binding ([product.rs:3630](../../crates/foundry-ledger/src/product.rs:3630)); an Owner task execution authorization, service DriveReview, ResolveReviewHold, and final ApproveOrder are distinct capabilities. Static consumer audit (deleg_83fcb5dc task 2) found no reachable ProductAtomicV1 approval/publish bypass without that binding, but is not a dynamic proof and excludes external clients. The scoped order API exposes `waiting` without a readiness indicator; standalone state-only consumers use a separately gated ledger contract. Importantly, HTTP/CLI call `prepare_approval` before `approve_product` ([approval_service.rs:133](../../crates/foundry-serve/src/approval_service.rs:133)); preparation may commit a reserved grant and a prepared operation with five-minute expiry ([product.rs:3256](../../crates/foundry-ledger/src/product.rs:3256), [3393](../../crates/foundry-ledger/src/product.rs:3393)). Failed final approval therefore does **not** imply the grant row is unchanged. Specify and test reservation, expiry/recovery and availability separately from grant/token consumption, S1 approval transition, approval outcome and result binding; do not infer UI or external-client safety from this static audit.

### Existing approval-reservation consequence — static analysis

The five-minute expiry is a **proof validity deadline, not an automatic grant release**. With the same authenticated actor, key, unchanged digest and matching current scope revision, a still-`prepared` operation returns the existing proof only when `now < expires_at`. For an expired, non-completed operation, the same-key retry attempts to reclaim its matching old fence and re-reserve; a new five-minute proof for the same operation is created **only if** the grant becomes `issued`, the token/actor/order binding remains exact, and the new reservation succeeds ([product.rs:3291-3377](../../crates/foundry-ledger/src/product.rs:3291), [grant participant](../../crates/foundry-approval/src/product.rs:42)). If the required exact result subsequently exists and all other current checks pass, the matching request may be approved; this is not a promise of success. Changing a bound tuple, artifact, run, generation or other digest field under the same key is an idempotency conflict even after expiry ([product.rs:3295](../../crates/foundry-ledger/src/product.rs:3295), [approval digest](../../crates/foundry-ledger/src/product.rs:5697)). A different key with the same still-reserved grant cannot prepare merely because five minutes elapsed: there is no automatic release established by this source. The explicit library recovery `fence_prepared_approvals` affects all prepared operations and increments recovery epoch, not just this grant ([product.rs:2486](../../crates/foundry-ledger/src/product.rs:2486)); the static audit found no product HTTP/CLI exposure. Do not invoke it as a routine single-request fix.

**Provisional W0 scope recommendation:** preserve current B1 prepare-first semantics; document the availability consequence rather than silently adding an automatic release or changing approval order. A pre-reservation result check, automatic cleanup, or targeted release would each be a separate B1 behavior/API change, not proven by A01. This is a candidate, not an accepted operational policy, and its exact user-facing recovery path remains unresolved. Source audit only; no new runtime tests were performed.
