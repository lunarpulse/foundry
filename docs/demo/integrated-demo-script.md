# Foundry 통합 시연 시나리오 스크립트 — 2면 구성

- **버전**: v1.0 (2026-10-12)
- **대상**: 비기술 투자자·관계자 (15분 구성)
- **무대**: ① 공개 GitHub 타임라인 (foundary-demo) ② 로컬 터미널 (원장·저널)
- **핵심 메시지**: *"AI가 일하고, 사람이 승인하고, 부정은 구조적으로 통과 못 한다 — 전부 번호(해시)로 증명된다"*

---

## 사전 준비 (시연 30분 전, 시연자 수행)

1. 헤드룸 있는 dep 확인: `curl crates.io/api/v1/crates/<dep>` — repo 버전 < max_stable 인 것
2. 시드 이슈 발행: `dep-bump: <dep>` (제목 규약 필수)
3. 터미널 2개 준비:
   - T1: `~/foundry` — 데모 실행용
   - T2: GitHub 저장소 커밋/PR 페이지 (프로젝터 분할 화면)
4. 사전 검증: `cargo build --example m8_publish` green

## 액트 2 — 주문 접수와 자율 구간 (3분)

**화면**: T1 터미널

```
cargo run -p foundry --example m8_publish -- --issue <N>
```

> "[1/8] 주문이 입장했습니다. 이슈 #N — 'serde_json 최신 버전으로 올려라'.
> 여기서부터 시스템은 **정해진 철도**만 달립니다:
> 에이전트가 저장소를 복제해오고(sandbox), 최신 버전을 **레지스트리에서
> 직접 조회**하고, 고친 뒤 컴파일 검증을 통과해야 커밋합니다."

** narration 포인트 (실행 중 수 분 대기 시간에 설명)**:
> "기다리는 동안 중요한 것 하나 — 이 시스템의 에이전트는
> **거짓 성공을 만들 수 없습니다**. 실제로 '이미 최신이라 고칠 게
> 없다'고 판단하면 그대로 보고하고 끝냅니다. 저번 사례(#139)가
> 그랬습니다 — 'rand는 이미 최신'이라 조사 근거를 붙여 거부했어요.
> 못 한 것을 했다고 우기는 에이전트가 아니라, 못 한 이유를 증명하는
> 에이전트입니다."

## 액트 3 — 승인 게이트: 번호의 순간 (3분) ★핵심 장면★

**화면**: T1 (종결 출력) → 곧바로 분할 화면 양쪽

터미널:
```
[3/8] 세그먼트 종결: FurnaceHold        ← 자율 구간 끝, 문이 닫힘
[4/8] 그랜트 CONSUMED — digest=4dbf4e749a57   ← 승인 원장에 번호 기록
```

> "여기가 이 시스템의 심장입니다. 에이전트가 만든 결과물에 번호가
> 찍혔습니다 — `4dbf4e749a57`. 제 승인 원장에 **같은 번호**가
> 기록됐습니다. 이제 발행 버튼을 누르면—"

```
PR 생성: https://github.com/lunarpulse/foundary-demo/pull/<M>
[6/8] Shipped 확정
```

**화면 전환**: GitHub PR 페이지의 head SHA — `4dbf4e749a57`

> "GitHub에 열린 PR의 번호와 원장의 번호가 **같습니다**. 결과물이
> 1글자라도 바뀌었으면 번호가 완전히 달라져서 이 문이 안 열립니다.
> 저는 에이전트를 믿을 필요가 없습니다 — **번호를 확인할 뿐**입니다.
> 믿음을 요구하는 시스템과, 검증만 요구하는 시스템. 후자가 이겁니다."

## 액트 4 — 고장 시나리오: 준비되어 있는 실패 (2분)

**화면**: GitHub 이슈/PR 목록 (#143 closed 항목)

> "'그런데 시스템이 죽으면?' — 지난주 실제로 일어났습니다(화면의
> #143). 발행 직전에 프로세스가 죽었죠. 시스템은 이때 **확정하지
> 않고** 미확정 상태로 보존합니다. 확인하고 정리한 건 사람 — 저입니다.
> 실패를 숨기는 게 아니라 **실패의 순간부터 인간 판정으로 돌아오도록
> 설계**돼 있습니다. 이것도 설계 문서에 있는 시나리오였고, 실제로
> 그대로 작동했습니다."

> 사람이 승인·머지, 기록은 전부 남음. 이게 전체입니다."

## 액트 6 — 마무리 한 장 (1분)

**화면**: 증명 결속 다이어그램

```
이슈 #N ──▶ 에이전트 산출물 ──▶ 승인 원장 ──▶ PR (head) ──▶ main 머지
 (사람 생성)    SHA 4dbf4e74…      SHA 4dbf4e74…    SHA 4dbf4e74…
                    └────────── 번호 일치 = 승인된 것만 발행 ──────────┘
```

> "정리하면 세 문장입니다.
> ① AI는 철도 위에서만 달린다 — 자유가 아니라 계약 안에서.
> ② 사람은 번호를 확인하고 판단한다 — 믿음이 아니라 검증으로.
> ③ 모든 단계가 번호로 묶여 나중에 누구나 검증할 수 있다 —
>    이 링크는 시연이 끝나도 살아있습니다."

## 예상 Q&A 대응

| 질문 | 답변 요지 |
|---|---|
| "AI가 엉뚱한 짓을 하면?" | sandbox 안에서만 작업, 결과물은 번호 결속 — 승인 안 되면 발행 자체가 불가. 과거 사례 #139처럼 '고칠 것 없음'도 증거와 함께 보고 |
| "해킹당하면?" | 승인 원장과 발행 자격이 분리 — 에이전트는 토큰을 못 봄(증명 구조상 발행은 별도 포트가 독점) |
| "dep-bump말고 복잡한 작업은?" | 이 시연은 '계약·게이트 구조'의 실증. 작업 복잡도 확장이 다음 마일스톤 — 구조가 검증됐으니 위에 얹는다 |
| "왜 GitHub가 무대?" | 신뢰 인프라를 우리가 만들 필요 없음 — 세계가 이미 쓰는 검증 가능한 기록. 우리는 그 위의 증명 계층 |
